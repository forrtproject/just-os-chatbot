How JUST-OS works

Two flows, top to bottom: what happens to one question, and how the index the answers come from is built. The page explains the logic, not the code. Every setting, model name, threshold and prompt below is read from the running app when the page loads (just_os/architecture.py): Code default is config/settings.py, This server is this app with its .env and AUTO_DEFAULTS applied, Prod is deploy/kubernetes/just-os.yaml (a value it does not set is the code default). Rows where this server and prod differ are shaded. Keys are never shown.

Flow 1: a question's journey

request → small talk? → answer cache? → follow-up rewritten → names a library paper? → topic check → (refuse | FORRT pages | papers) → search → filter and cut → answer model → citations and Sources box → stored in the chat memory

{% call step("q-request", "1. The request: what the page or widget sends to POST /chat", "both") %}

The forrt.org widget (prod) and the built-in chat page (dev) send one JSON object per question:

{"message": "{{ question }}",      // required, {{ s.value('MIN_MESSAGE_LENGTH') }} to {{ s.value('MAX_MESSAGE_LENGTH') }} characters
 "chat_id": "3f2a…",              // required: the chat's memory key
 "model": "…",                    // optional: answer model (dev page; must be in its list)
 "router": "banded",              // optional: topic check for this question (dev page dropdown)
 "stream": true,                  // optional: send the answer while it is written
 "debug": true}                   // optional: the debug panel's trace (dev page with ?debug=1)

The answer comes back as a stream of JSON lines: progress lines ({"status": "in-progress", "message": "Classifying question"}, then "Finding relevant sources", "Generating response"), with stream pieces of the answer ({"status": "partial", "delta": "…"}), and one final line {"status": "complete" | "error", "message": "<p>HTML…</p>", "outcome": …, "metadata": {"sources": text, "references": [ … ]}, "timings": {"classify_s", "search_s", "answer_s", …, "total_s"}}. On dev the final line also has a turn_id (for the Good/Bad buttons) and, when asked, debug.

  • Missing message/chat_id, a message too short or long, an unknown model or topic check: HTTP 400.
  • More than RATE_LIMIT requests from one IP: HTTP 429 (counted in Redis; behind a proxy the client IP comes from X-Forwarded-For when PROXY_FIX_X_FOR is set).
  • Only ALLOWED_ORIGINS may call /chat from another website (CORS).
  • prod only PROD_MODE: the only allowed model is CITATION_MODEL, debug is ignored, and no turn_id is sent.
{{ cfg(["MIN_MESSAGE_LENGTH", "MAX_MESSAGE_LENGTH", "RATE_LIMIT", "PROXY_FIX_X_FOR", "ALLOWED_ORIGINS", "PROD_MODE", "DEBUG_PANEL"]) }} {% endcall %} {% call step("q-small-talk", "2. Small talk: greetings, thanks, \"who are you?\"", "both") %}

Before anything else, a pattern test: a message that is only a greeting, thanks or a question about the bot itself ("Hi!", "Who are you?", "Hello, what can you do?") gets the short self-introduction (the about text of config/refusals.csv, in the question's language). No model call, no search. Outcome small_talk. This runs before the follow-up rewrite, so "thanks" after an answer is not turned into a question.

{% endcall %} {% call step("q-cache", "3. Answer cache (first question of a chat only)", "both") %}

When ANSWER_CACHE_TTL is above 0, the first question of a chat is compared with recent first questions (cosine of their bge-m3 vectors). At or above ANSWER_CACHE_MIN_SIMILARITY the stored answer is sent again: no topic check, search or model call. One cache per setup: the entry is only reused when these settings are the same: {{ c.cache_keys | join(", ") }} (and the chosen answer model). The cache lives in Redis, shared by all users, at most ANSWER_CACHE_MAX_ITEMS entries. On this server it is {{ "on" if s.value('ANSWER_CACHE_TTL') not in ("0", "(empty)") else "off" }}.

{{ cfg(["ANSWER_CACHE_TTL", "ANSWER_CACHE_MIN_SIMILARITY", "ANSWER_CACHE_MAX_ITEMS"]) }} {% endcall %} {% call step("q-follow-up", "4. Follow-up questions: rewritten into a stand-alone question", "both") %}

The chat memory (Redis, see Redis) holds the earlier turns. The first question of a chat is used as typed. For a follow-up, CONTEXT_METHOD decides (this server: {{ s.value('CONTEXT_METHOD') }}):

  • rephrase: one call to GENERAL_MODEL ({{ s.value('GENERAL_MODEL') }}) rewrites the follow-up into one question that makes sense alone; everything after uses the rewrite.
  • hybrid: the same rewrite for the topic check and the search; the answer model gets the last {{ c.history_turns }} messages of the chat and the question as typed, plus "(Meaning: the rewrite)" when it differs.
  • history: no rewrite; the search sees the last user question plus the new one, and the answer model gets the last {{ c.history_turns }} messages.

In the prompt, the bot's earlier answers are cut to {{ c.rephrase_answer_chars }} characters, so the rewrite takes its words from the user. A rewrite that grows by more than {{ c.rewrite_max_added_words }} words (and more than twice the question) has pulled in an answer: the question as typed is used instead. If the call fails, also the question as typed. The model is asked for one JSON value ({{ prompts.rephrase.key }}) through a forced tool call at temperature {{ prompts.rephrase.temperature }}; models without tool calls are asked again for plain JSON.

With REFERENCE_LOOKUP on, the question as typed (then the rewrite) is checked against every paper of the index (not the glossary): a DOI in the question; a title (all its content words, for titles of at least {{ c.min_title_words }} words, or {{ (c.title_coverage * 100) | round | int }}% of them when the question refers to a work: "paper", "et al.", a year, quotes; or its short title before the colon); or authors (two surnames of one paper, or one surname and its year). More than {{ c.max_matches }} matching papers is too vague: the normal search runs.

  • DOI or title match: no topic check; the answer comes from that paper's chunks only, the MAX_CHUNKS closest to the question, any number per paper, without the similarity floor.
  • Author match: the topic check still runs. If it says FORRT, the match is dropped (a person or a FORRT project); if it says off topic, it is overruled (two of a library paper's authors were named).
{{ cfg(["REFERENCE_LOOKUP"]) }} {% endcall %} {% call step("q-topic", "6. Topic check: answer from the papers, from FORRT's pages, or refuse?", "both") %}

If the model cannot be reached the user gets the "model unavailable" message, never a refusal. This server's default: {{ s.value('ROUTER') }}.

Similarity (cosine, banded)

The question is turned into a bge-m3 vector and compared with two things: the nearest paper chunk of the index and the nearest FORRT page description (FORRT_PAGES_DIR). Cosine 1 = same direction, 0 = unrelated. The two numbers are on different scales (short descriptions vs. passages), so each has its own thresholds.

  • cosine: paper ≥ COSINE_PAPER_MIN ({{ s.value('COSINE_PAPER_MIN') }}) → papers; page ≥ COSINE_PAGE_MIN ({{ s.value('COSINE_PAGE_MIN') }}) → FORRT pages; both → the higher number; neither → off topic.
  • banded: paper < {{ s.value('BAND_PAPER_LOW') }} and page < {{ s.value('BAND_PAGE_LOW') }} → off topic, no model call. Paper ≥ {{ s.value('BAND_PAPER_HIGH') }} and page < {{ s.value('BAND_PAGE_HIGH') }} → papers, no model call. Everything else (the middle band, and every question close to a FORRT page) → BAND_MIDDLE_ROUTER ({{ s.value('BAND_MIDDLE_ROUTER') }}). Similarity alone never sends a question to FORRT's pages.

Decision models (Jev, Clef, Clef-flash)

A decision model does not write text: it gets the question and the four options and returns a probability for each (OpenRouter's decisions API, DECISION_URL, about 0.3–2 s, its own key DECISION_API_KEY, on prod too: uniGPT has no decision models). The default route takes its answer only when it is at least DECISION_ROUTER_MIN_CONFIDENCE sure; a router picked by name takes any answer. "neither" means off topic.   1. Find candidate pages: the question vector against the page index (links and short LLM-written descriptions of forrt.org pages, not their content), plus FORRT_LEXICAL_WEIGHT × word overlap, plus, for "news / events / upcoming" questions, a recency bonus (FORRT_RECENCY_WEIGHT, halving every FORRT_RECENCY_HALF_LIFE days). The top FORRT_TOP_K pages.
  2. Pick pages: the decision model FORRT_SELECT_MODEL answers yes/no per page ("Would reading this page help?"). Pages at or above FORRT_DECISION_THRESHOLD are read, at most FORRT_MAX_PAGES. If none, but the best is above FORRT_DECISION_FLOOR: the plausible ones (up to 3) plus the top search result. If the call fails: the top search results.
  3. Read them live from forrt.org (only FORRT_FETCH_DOMAINS; kept in memory FORRT_CACHE_TTL s), each cut to the FORRT_MAX_CHARS_PER_PAGE characters that best match the question.
  4. Answer with the prompts below (temperature 0, at most FORRT_MAX_ANSWER_TOKENS tokens), in the language of the question as typed.
  5. Checks in code: wrong language, or past events called upcoming → one rewrite with the problems listed; links that are not on the pages are removed; citation numbers are cleaned. The pages go to the Sources box.

Reciprocal rank fusion: a chunk's score is the sum of 1 / ({{ c.rrf_k }} + rank) over both lists.

RERANK off: keep the search order

If the best vector match has a cosine below MIN_VECTOR_SIMILARITY ({{ s.value('MIN_VECTOR_SIMILARITY') }}), the answer is "no sources" (no model call). Not in bm25 mode (no fixed scale). Then the filters of step 10.

RERANK on

A cross-encoder (RERANK_MODEL) reads each (question, "Title: … Text: …") pair and scores it; chunks at or below MIN_RELEVANCE are dropped and the rest sorted by that score. No similarity floor and no cluster boost. If the re-ranker fails, the search order is kept.

ADAPTIVE_TOP_K ({{ s.value('ADAPTIVE_TOP_K') }} here) keeps only chunks scoring at least ADAPTIVE_TOP_K_RATIO of the best one, but at least ADAPTIVE_TOP_K_MIN.

{{ cfg(["SEARCH_MODE", "RETRIEVER_TOP_K", "MIN_VECTOR_SIMILARITY", "RERANK", "RERANK_MODEL", "MIN_RELEVANCE", "ADAPTIVE_TOP_K", "ADAPTIVE_TOP_K_RATIO", "ADAPTIVE_TOP_K_MIN"]) }} {% endcall %} {% call step("q-filter", "10. From the candidates to at most " ~ s.value('MAX_CHUNKS') ~ " passages", "both") %}

In this order:

  1. Cluster boost (vector search, RERANK off; CLUSTER_BOOST = {{ s.value('CLUSTER_BOOST') }}, 0 = off): each FORRT cluster has a centroid (mean vector of its documents' chunks). When the question is closer to one cluster's centroid than to the next by CLUSTER_BOOST_MARGIN, that cluster's chunks get CLUSTER_BOOST added to their cosine and the candidates are re-sorted.
  2. Wrong documents out: documents listed under exclude in INDEX_CORRECTIONS_FILE (their text is another work) are dropped.
  3. Reference lists out (SKIP_REFERENCE_CHUNKS = {{ s.value('SKIP_REFERENCE_CHUNKS') }}): a chunk with more than {{ c.citations_per_100_words }} citation patterns ("(2013)", "et al.", "12(3)", page ranges) per 100 words, or fewer than {{ c.min_words }} words, is dropped. Glossary entries and abstract cards are short on purpose and stay.
  4. One glossary entry: the FORRT glossary has the same term in five languages, which would fill the slots. Only one stays: the best-ranked entry in the question's language, else in English, else the best one. Then the search picks the term and the question picks the language (same_term_in): the found entry is swapped for the same term in the question's language, else English. Language map: {{ c.glossary_languages | tojson }}. The entry and the papers it cites move to the front.
  5. At most MAX_CHUNKS_PER_DOC ({{ s.value('MAX_CHUNKS_PER_DOC') }}) chunks per document, for variety.
  6. Cut to MAX_CHUNKS ({{ s.value('MAX_CHUNKS') }}).

Nothing left: "no sources".

The forrt.org widget talks to the Kubernetes deployment (or the web-prod service of Docker Compose): two web pods and one Redis. PROD_MODE is true there: nothing is saved (no chat log, feedback or arena files, no feedback:turn keys), no Good/Bad buttons, no debug panel, only CITATION_MODEL on the chat page, and all team pages (/eval, /review, /topics, /arena, /recommend, /articles, /architecture) answer 404. Flow 2: the index

sources → Markdown → chunks of {{ s.value('CHUNK_SIZE') }} tokens + metadata → {{ s.value('EMBEDDING_MODEL') }} vectors → FAISS store → searched per question → passages for the answer model

{% call step("i-inputs", "1. The raw inputs", "dev") %}
  • FORRT sheets and lists: the resources FORRT wants in the bot (FORRT_SHEET_FILE; merged into the article list CLUSTERS_FILE by scripts/forrt_article_list.py, shown on /articles).
  • The original JUST-OS library: PDFs converted with marker, with metadata from the JUST-OS database.
  • FORRT cluster PDFs: the PDFs of the clusters (scripts/convert_cluster_pdfs.py).
  • Curated additions: ./run curate takes the FORRT sheets, a CSV, or what people sent on /recommend (RECOMMENDATIONS_FILE), finds an open copy by DOI (row link, arXiv/OSF, Unpaywall, OpenAlex, Semantic Scholar, Europe PMC, publisher page) or, without a DOI, the web page.
  • Web pages: FORRT resources without a DOI, their main text (scripts/fetch_web_resources.py).
  • FORRT glossary: _glossaries.json of the forrt repository, one document per term and language (scripts/build_glossary.py).
  • Abstract cards: resources without full text (paywalled, books): title, authors, year, cluster, FORRT summary, abstract and link as one short document (scripts/build_abstract_cards.py).
  • Separate from the index: the FORRT page index (FORRT_PAGES_DIR), links and descriptions written by FORRT_DESCRIBE_MODEL (scripts/build_forrt_pages.py); page content is always read live.
{{ cfg(["FORRT_SHEET_FILE", "CLUSTERS_FILE", "RECOMMENDATIONS_FILE", "FORRT_PAGES_DIR", "FORRT_DESCRIBE_MODEL"]) }} {% endcall %} {% call step("i-markdown", "2. Everything becomes Markdown", "dev") %}
  • PDF → GROBID (curate, cluster PDFs): body text without the reference list and page headers, plus title, authors, DOI. A found copy is kept only when its title matches. Books (over 80 pages) and PDFs where GROBID finds almost no body: pymupdf4llm. Scans are rejected.
  • PDF → marker (scripts/marker.sh): the original JUST-OS library.
  • Web page → main text: the page without menus and footers. Licence unknown, so no quotes are shown.
  • Glossary: title, definition and related terms; the entry's reference list goes to the metadata (reference_dois), not the text.
  • Clean-up before chunking: in-text citation numbers like "[12]" are removed.
{% endcall %} {% call step("i-chunks", "3. Chunks and their metadata", "dev") %}

Each document is split into chunks of about CHUNK_SIZE = {{ s.value('CHUNK_SIZE') }} tokens, at sentence boundaries, overlapping by {{ c.chunk_overlap }} tokens (llama-index SentenceSplitter). Every chunk keeps its document's metadata (title, creators, DOI, link, licence, material type, language, …). {% if example and example.chunk %}Only what the chunk's text template {{ example.chunk.template }} contains is embedded{% if example.chunk.template == "{content}" %}: the chunk text alone, so a title, author or DOI in the question does not find its paper (that is why step 5 of Flow 1 exists){% endif %}.{% endif %}

{% endif %} {{ cfg(["CHUNK_SIZE", "VECTOR_STORE"]) }} {% endcall %} {% call step("i-embed", "4. Vectors and the FAISS store", "dev") %}

Each chunk's text becomes one vector of EMBEDDING_MODEL ({{ s.value('EMBEDDING_MODEL') }}, multilingual, so a German question finds English text){% if example and example.dimension %}: {{ example.dimension }} numbers, scaled to length 1{% endif %}. The vectors go into a FAISS store{% if example and example.faiss %} ({{ example.faiss }}, {{ "{:,}".format(example.chunks) }} chunks){% endif %}: an exact search that compares the question with every chunk. The chunk texts and metadata are in docstore.json next to it. The question uses the same model, so both are in the same space.

{{ cfg(["EMBEDDING_MODEL", "VECTOR_STORE"]) }} {% endcall %} {% call step("i-add", "5. Adding, fixing and removing documents", "dev") %}
  • Adding: scripts/add_to_index.py (used by ./run curate, the glossary and the abstract cards) embeds only new documents and appends them; a document whose DOI or title is already in the index is skipped. ./run curate writes a copy (data/processed/vs_curated_<YYMMDD>) unless --in-place; point VECTOR_STORE at the new folder and restart.
  • FAISS IndexFlatL2 cannot delete a vector. So a wrong document stays in the store and is filtered out instead: exclude in INDEX_CORRECTIONS_FILE (text of another work; never returned by the search or the reference lookup). Wrong titles are corrected in the metadata only by scripts/fix_index_titles.py (the vectors came from the text, which is right).
  • A full text joins its abstract card: cards do not count as "already in the index", so the full text is added; the card stays, and the per-document limit counts both as one document.
  • Full rebuild: scripts/embed.py builds a new store from all Markdown; then the add steps again. Only a rebuild really removes documents and leftover cards. scripts/reembed.py copies an index to another embedding model.
{{ cfg(["INDEX_CORRECTIONS_FILE", "VECTOR_STORE"]) }} {% endcall %} {% call step("i-search", "6. How search works in that space", "both") %}

The question becomes a vector of length 1 the same way. FAISS returns the RETRIEVER_TOP_K ({{ s.value('RETRIEVER_TOP_K') }}) chunks with the smallest squared distance d. For vectors of length 1, cosine = 1 − d/2, so the smallest distance is the highest cosine: 1 means the same direction. All the thresholds of Flow 1 (MIN_VECTOR_SIMILARITY, COSINE_PAPER_MIN, the bands) are on that cosine scale.

{% endif %} {{ cfg(["RETRIEVER_TOP_K", "MIN_VECTOR_SIMILARITY"]) }} {% endcall %} {% call step("i-llm", "7. What finally reaches the answer model", "both") %}

Of the whole index, at most MAX_CHUNKS ({{ s.value('MAX_CHUNKS') }}) passages, plus up to FORRT_IN_PAPERS_MAX_PAGES forrt.org page excerpts, each as "[n] Title: … Text: …", with the question and the prompts of Flow 1 step 12. The model never sees the rest of the index, the metadata (except titles) or the scores.
